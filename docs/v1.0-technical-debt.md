# AI OS v1.0 Technical Debt

Date: 2026-08-26

This document classifies known v0.9.0 limitations and baseline audit findings for the v1.0 hardening milestone.

## Critical For v1.0

### Malformed approval-store records

Status: fixed

Risk: malformed records in `.ai-os/approvals/approvals.json` could trigger unsafe direct-key lookups, including the pre-existing `KeyError` noted in v0.9.0.

Resolution:

- Approval reads now validate that the store root is a list.
- Approval ID generation ignores malformed records instead of crashing.
- Approval list, lookup, update, reject, and approval checks use safe access.
- Malformed records are preserved for validation visibility rather than silently deleted.
- Orchestration validation avoids direct `target` assumptions when collecting approved memory-suggestion approvals.

Tests:

- `test_malformed_approval_record_does_not_crash_read_operations`
- `test_request_approval_preserves_malformed_records_and_generates_id`

Validation:

- `python -m pytest tests\test_orchestration_approvals.py tests\test_release.py -q` passed: 72 passed.

### Status command reports release readiness from file existence only

Status: fixed

Risk: `python scripts/ai-os.py status` reported `Release ready: True` while `release-check` and `validate-all` failed. This could mislead a release operator.

Resolution:

- Status now runs existing generated-artifact freshness checks.
- Status exposes `generationChecks` and `summary` in JSON.
- Human-readable status reports subsystem results and `Overall: NOT READY` when generated artifacts are stale.
- Existing JSON fields such as `version`, `artifacts`, `dashboard`, `mcp`, and `releaseReady` remain compatible.

Tests:

- `test_status_release_ready_requires_current_generated_artifacts`
- Updated CLI status assertion for the new `Overall:` summary.

## Recommended For v1.0

### Stale generated artifacts

Status: fixed

Reason: Generated-artifact regeneration was non-idempotent -- `python scripts/ai-os.py build` and
`python scripts/dashboard-build.py` rewrote `generated/release-manifest.json`/`.md` and
`generated/dashboard-data.json`/`dashboard.html` on every run even with no meaningful source
change, because volatile fields (`generatedAt`, and a filesystem-mtime-derived `fileTimestamp` in
the dashboard artifact) were committed content and the writers never compared against existing
committed output before overwriting it.

Resolution:

- `scripts/release/manifest.py` gained `write_manifest_if_changed()`, which compares the freshly
  built manifest against the committed one (ignoring only `generatedAt`, exactly as `check_manifest`
  already did) and leaves the file untouched when normalized content is unchanged.
  `scripts/ai-os.py`'s `build` command now calls it instead of writing unconditionally.
- `scripts/dashboard-build.py` gained the same current-vs-committed comparison before writing.
- The `fileTimestamp` field in `generated/dashboard-data.json` (derived from filesystem
  modification time via `scripts/dashboard/aggregate.py`) was removed outright, since filesystem
  mtimes vary across clones/computers and must never be committed content; `generatedAt` (a
  content-derived field written once at generation time) already served the same purpose.

Tests: `tests/test_release.py::ManifestIdempotencyTests`,
`tests/test_release.py::BuildTests::test_build_second_run_no_git_diff`,
`tests/test_dashboard.py::DashboardIdempotencyTests`.

Validation: two consecutive `python scripts/ai-os.py build` runs and two consecutive
`python scripts/dashboard-build.py` runs each produce a byte-identical result on the second run;
`git diff --check` passes after regeneration. See
[docs/v1.0-final-acceptance.md](v1.0-final-acceptance.md).

### CI trigger and Python-version hardening

Status: fixed

Reason: `.github/workflows/validate.yml` pins Python to `3.12`, triggers only on push/PR to `main`
plus manual `workflow_dispatch`, sets `permissions: contents: read`, defines a `concurrency` group
with `cancel-in-progress: true`, and runs a dedicated `Diff Hygiene` job (`git diff --check`)
alongside repository validation, unit tests, MCP smoke tests, and release readiness.

### Portable MCP setup

Status: fixed

Reason: `docs/multi-device-setup.md` now documents clone/setup/troubleshooting steps using
`<REPOSITORY_ROOT>` placeholders instead of a committed user-specific absolute path, and
`scripts/mcp-server.py`'s `resolve_root()` honors `AI_OS_HOME` when it points at a valid AI OS
root and safely falls back to the repository containing `scripts/mcp-server.py` otherwise.
Re-verified on this machine: MCP starts correctly with `AI_OS_HOME` unset, with `AI_OS_HOME` set to
an invalid path, and with `AI_OS_HOME` set to a separate valid root -- see
[docs/v1.0-final-acceptance.md](v1.0-final-acceptance.md).

### Repository ownership references

Status: fixed

Reason: `docs/repository-migration.md` documents the completed migration from `frojas15` to
`felipedr15/ai-skills-pack`. The only remaining `frojas15` mentions in the repository are
intentional history: `docs/v1.0-baseline-audit.md` (a dated snapshot of the pre-migration state,
which must not be rewritten), and `RELEASE_NOTES_v0.8.0.md` (an already-published historical
changelog referencing the real PR author and URLs at that time). `generated/discovery-index.json`
only mirrors those legitimate historical mentions through normal content indexing.

Note: a local machine's Git remote (e.g. a clone made before the migration) is local, per-clone
configuration -- it is not committed repository content and is out of scope for this check. This
computer's local `origin` remote was found still pointing at the old `frojas15` URL at the start of
this work and was updated to `https://github.com/felipedr15/ai-skills-pack.git` as a local,
non-committed step; see [docs/v1.0-final-acceptance.md](v1.0-final-acceptance.md).

### Sanitization language

Status: fixed

Reason: `SECURITY.md` and `knowledge/architecture/phase-9-professional-context.md` both state
plainly that `scripts/profile/sanitize.py` sanitization is deterministic and regex-based, that it
reduces risk but is not a substitute for human privacy review, and list a stronger sanitizer as an
explicit non-goal for this release.

## Deferred After v1.0

### Approval expiration

Status: deferred

Reason: The current approval model already fails closed for non-`approved` statuses, including a future `expired` status. Adding wall-clock expiration would require policy decisions for retention, display, and audit semantics. v1.0 keeps historical approvals intact and does not silently expire or delete them.

### `scripts/profile/` shadows Python standard-library `profile`

Status: deferred

Reason: Renaming the package would touch a broad import surface across CLI, tests, dashboard, MCP, and generated artifacts. The current issue is documented, and no active runtime bug was isolated during the baseline audit.

### Live `.ai-os/sessions/` excluded from committed work activity

Status: no longer considered a defect

Reason: This is an intentional deterministic-generation boundary. Local runtime state remains excluded from committed generated artifacts so output stays portable across machines.

### `windowDays` is descriptive metadata

Status: deferred

Reason: Implementing a wall-clock activity filter changes semantics and may make generated artifacts time-dependent. v1.0 should preserve deterministic generation.

### Richer role/team/expertise graph relationships

Status: deferred

Reason: Current graph exposure intentionally avoids leaking detailed profile content through general traversal. Broader professional graph semantics need a privacy review before implementation.

### Evidence-resolution status in MCP/dashboard

Status: deferred

Reason: Useful, but not required to preserve core release gates. It should be added only with careful summary-only exposure.

## Environment Issue Tracked From Baseline

Running tests inside the managed sandbox on Windows/Python 3.14.4 caused widespread `PermissionError` failures for temporary directories under `AppData\Local\Temp` and test-created `pytest-cache-files-*` directories. The same targeted test set passed outside the sandbox. This is tracked as an execution-environment issue, not as proof that the affected application modules are broken.
